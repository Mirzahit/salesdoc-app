## 1. Диагноз — три корневые причины

### 1.1. «Действующие» ≠ `clients.status = 'active'`
Список строится на фронте из **статического `clients-kz.json`** (254 записи без статуса и `client_id`) + **всех** клиентов Supabase любого статуса (`index.html:42775` — без `status=`) + псевдо-клиентов из localStorage. «Действующий / просрочен / ушёл» вычисляется по **платежам, сгруппированным по текстовому имени компании** (`:43205`), `client_id` платежа не используется.

Одновременно живут **четыре** правила «до какого числа оплачено»:
| Кто | Правило | Где |
|---|---|---|
| Фронт «Действующие» | конец месяца (дата+период), без +1 | `index.html:43224` |
| Фронт «Ожидание оплат» | по месяцам, `lost` через 3 мес | `:44095-44158` |
| Бот «абон.плата» | `сегодня + период` (от даты приёма) | `api/cards.js:476` |
| Крон `recalcBilling` | конец месяца + 1, **только повышает** | `api/clients.js:41-116` |

Пример: оплата 10.05 на 1 мес через бот → в БД `next_billing_at=10.06`, крон считает 01.06, но «не откатывает» → напоминания идут 3–10 июня, а экран уже 5 дней показывает «отвалился».

### 1.2. Активация с доски минует серверную логику
`finishImplementation` (`api/cards.js:61-78`) пишет `status='active'` напрямую → последующий `PATCH status:'active'` с фронта (`index.html:32171`, `:34727`) получает `already_active` и **отбрасывает тело** (`api/clients.js:385-387`). Итог: у клиентов, дошедших до последнего этапа, **не ставятся** `next_billing_at`, период, `curator_operator`; напоминания молчат. Плюс:
- `activation_date` по UTC (`cards.js:72`), а не Алматы;
- последний этап захардкожен как «Активация» (`index.html:32172, 34706, 34212`) при настраиваемых этапах;
- «Передать в Действующие» глотает ошибку и всё равно архивирует карточку (`:34870`) → клиент в лимбо (нет ни на доске, ни в действующих);
- «кто ведёт» — два поля: доска пишет `support_operator`, кнопка/массовое назначение — `curator_operator`, напоминания читают только `curator_operator` (у 452 из 538 пуст).

Ухода из «Действующих» автоматически **нет вообще**: только ручной статус; бот при повторной оплате ушедшего не реактивирует.

### 1.3. Командные данные живут в localStorage, карточка — «внедренческая»
- Теги (`crm_client_tags`), привязки платежей (`sd_pay_overrides`, `sd_pay_skip_match`, `sd_prefix_approved`), «отдельные клиенты» (`sd_additional_clients`), кэш оплат 2025 без TTL — **у каждого оператора своя картина**; теги переопределяют риск (`:43368`) и не видны ни CEO, ни в карточке.
- Карточка действующего клиента — та же `#view-route-card` внедрения: «Назад во Внедрение», пустой пайплайн, «Сделка» с прочерками, подсказка «Возьмите карточку», вкладка «История» скрыта. Нет: статуса доступа в шапке, вкладки «Оплаты», тегов, объяснения «почему горит».
- Единой хронологии нет: `card_history` + `client_notes` + `tasks` + `tickets` + `churn_notes` (без `client_id`) + `notifications`. **Не логируются**: смена статуса, смена куратора, теги, получение оплаты, продление ботом, завершение внедрения, архивация.

## 2. Целевая модель

### 2.1. Сервер — единственный источник истины
```
clients.status ∈ lead | sale | onboarding | active | paused | churned
clients.access_until   date   -- max(конец месяца(paid_at+period)) по subscription+license, учёт free_until
clients.access_status  text   -- active | expiring (≤7 дн) | grace (0–6 дн просрочки) | overdue (≥7) | none
clients.next_billing_at = access_until + 1 день
clients.next_billing_source ∈ calc | bot | manual   -- manual не перезаписывается кроном
clients.support_operator  -- «Куратор» (кто ведёт). Единственное поле для напоминаний, списка, массового назначения
clients.curator_operator  -- «Кто продал» (из amo), read-only в UI
clients.churned_at, churn_reason
```
Новые таблицы: `client_tags (client_id, tag, created_by, created_at)`, `payment_links (country, pay_host, client_id | separate_name | skip, decided_by, decided_at)`.
SQL-view `client_timeline` — union `card_history` (по client_id и всем картам клиента) + `client_notes` + `tasks` (создана/закрыта) + `tickets` + `payments` + статусные переходы.

### 2.2. Жизненный цикл (все пути через одну функцию)
`activateClient(client_id, {operator, period, actor, source})` в `api/clients.js`:
1. `status='active'`, `activation_date=almatyIso()` если пусто, `support_operator` если пусто;
2. `subscription_period_months`, `next_billing_at` по календарному правилу;
3. запись `card_history(event_type='system', text='Переведён в действующие · по завершении внедрения · Айдос')`.

Вызывается из: последний этап доски (`cards.js`), кнопка «Активировать», чек-лист «Передать», inline-статус, POST с `status:'active'`, импорт, реактивация ботом. Архивация карточки и активация — одна операция (не архивировать при ошибке).

Переходы статуса (сервер, `PATCH`): любая смена → `card_history(system)` с актором. `active→churned/paused`: причина обязательна, `churned_at`. `churned/paused→active`: сброс `pay_reason`, `churned_at`.

**Автоматика (крон, раз в 2 ч, после recalc):**
- `access_status` пересчитывается для всех статусов;
- подписочная оплата у `paused/churned` → `activateClient(source='bot')`;
- `overdue ≥ N дней` (N из `app_settings`, по умолчанию 30) → `paused` автоматически, с записью «автоматически · нет оплаты 30 дн»;
- `churned` — **только вручную** с причиной (решение владельца, см. §5).

### 2.3. Список «Действующие» (фронт)
Источник: `/api/clients?country=X&status=in.(active,paused)` + серверные `access_*`. Убираются: `clients-kz.json`, `window._acPriorPays`, локальный расчёт доступа, все `AC_*` localStorage-ключи (кроме UI-предпочтений).

**Сценарий оператора (главный):** «у кого горит → позвонить → записать». Всё остальное вторично.

**«Горит»** (одно определение для списка, сигналов и цифры CEO): `access_status ∈ expiring | grace | overdue` **и** за последние 7 дней нет контакта (заметки/задачи) **и** `next_step_at` не в будущем. После записи «следующий шаг до даты» клиент перестаёт «гореть» до этой даты.

**Быстрая заметка из строки** (без открытия карточки): текст + «следующий шаг до …» → пишет `card_history(note)` и `clients.next_step_at / next_step_text`; обновляет колонки «Последний контакт» и «Следующий шаг».

**Тулбар (MVP):** поиск (hotkey `/`) · сегмент-контрол **Горит · Мои · Все** · дропдауны Куратор / Сегмент / Теги (внутри — «Без куратора», «Истекает в этом месяце», «На паузе») · Сбросить. Дефолт для оператора — **Мои · Горит**, сортировка по срочности.
**Стат-строка:** CEO/руководитель — «горящих вчера 12 · обработано 9», MRR, удержание, разрез по кураторам (раскрывающийся); оператор — «Мои: 42 · горит 5 · без задач 12».
**Таблица:** ☐ · Клиент (имя, сервер) · Доступ (пилюля + дата) · Абонплата · Польз. · Куратор (чип → поповер смены) · Теги · Последний контакт · Следующий шаг · ⋯. Сортировка по колонкам, пагинация по 100. Меню ⋯: Открыть карту · Позвонить · WhatsApp · Заметка · + Задача · Внести оплату · Сменить куратора · Теги. Кнопка «Позвонить» только если есть телефон (проверить заполненность `main_phone` SQL до этапа 3).
**Массовые (MVP):** назначить куратора (`support_operator`, батч-endpoint). Позже: задача, тег, CSV, настройка столбцов.
**Состояния:** skeleton 8 строк; ошибка — «Не удалось загрузить список · Повторить»; пусто — без «нажми ↻».
**Клавиатура (MVP):** `/` поиск, Esc — закрыть карту/панель. ↑/↓/Enter — позже.
**«Требуют внимания»** (сверка оплат без клиента / требуют подтверждения) — отдельный этап после карточки, для бухгалтерии/CEO; данные в `payment_links`.

### 2.4. Карточка клиента — режим `client`
Переиспользуем `#view-route-card`, добавляем режим (`card.mode='client'`), в котором скрыты пайплайн, «Сделка», подсказка «Возьмите карточку»; «Назад» → список.

**Шапка:** имя · сервер · страна · пилюля **«Действующий · доступ до 30.09 (через 17 дн)»** · Куратор (чип-поповер) · сегмент «B · 14 польз.» · абонплата · теги · действия: Позвонить · WhatsApp · + Задача · + Обращение · Внести оплату · ⋯ (Сменить статус, Передать).
**Табы (MVP):** Обзор · Оплаты · Контакты · Документы. Хронология — правая колонка Обзора (как сейчас лента), с фильтрами Все / Заметки / Задачи / Оплаты / Обращения / Изменения и «Показать ещё». Отдельные табы Задачи/Заметки/Обращения не делаем — дублируют ленту.
- *Обзор*: слева карточки «Доступ» (до / период / лицензии / тариф), «Кто ведёт» (куратор, кто продал), «Сигналы», «Следующий шаг»; справа — хронология из существующих `card_history` + `client_notes` + `tasks` + `payments` (SQL-view `client_timeline` — позже, когда источников станет больше).
- *Оплаты*: таблица (дата, сумма, категория, период, банк, кто внёс, продлил до) + «Внести оплату».
**Провенанс** — мелкая строка `.fld-prov` **только** на пилюле доступа и на кураторе: «автоматически · по оплате 12.05», «вручную · Айдос · 12 мая». Слов «ИИ / ассистент / сгенерировано» в операционных экранах нет.
**«Сигналы»** — детерминированные правила вместо ИИ-инсайтов: «Доступ истекает через 3 дня», «Нет оплат 45 дн при 12 платежах в истории», «Лицензий стало меньше: 14 → 9», «Открытое обращение 6 дн», «Просроченная задача», «Нет куратора». У каждого — кнопка действия.
